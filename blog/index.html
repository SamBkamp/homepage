Understanding Clone - a weird linux syscall

The clone syscall is a niche one, It's hard to find info on the internet on how it works, and even less info about the newer clone3() call. So, why did I decide to use it?

it started with this talk from Liz Rice on containers where she, live on stage, demonstrated how to build a basic container in go from scratch. This enthralled me, I always thought containers were essentially Virtual Machines with stripped down OS' (without GUIs and without most device drivers), it turns out containers are more closely related to ftp servers than VMs. Instead of virtualising a whole operating system, containers are essentially jailed processes, much like how ftp servers give access to jailed users.

The core difference between a container and an FTP server (besides the obvious) is that the jailing expands far further than just chroot. This introduced me to a concept in Linux I had not really heard about before: namespaces. While the average linux user definetly interfaces with them, we rarely see, and therefore comprehend, the depth of these namespaces in casual use.

Looking at the man pages (namespaces(7)) it seems that the primary use of these namespaces is to implement containers specifically, I can't think of any other use of namespaces but I don't think it really needs any more. There exist 8 namespaces that isolate different aspects of a program:

As you can tell, these are quite critical to containerisation and effective jailing of processes.

So about clone3()....

what does clone3() actually do? First lets clear up some potential confusion (last bit of frontloading I promise): There are 2 versions of the clone syscall you can call from C. First you have the glibc clone() function, hereafter called "glibc clone", and the "raw" syscall, hereafter simply called "clone" or "clone3". The glibc clone is a simplified but also more dated version of the call, in this article i'll mainly be talking about the more direct raw clone syscall though.
